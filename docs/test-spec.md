# テスト仕様書 — 脱炭素ニュースポータル（NewsPortal-DEC）

最終更新: 2026-07-10

## 0. 現状の位置づけ

**本リポジトリには自動テストコード（単体テスト・E2Eテストのいずれも）は存在しない。**
これまでの品質担保は、実装のたびに以下を都度手動で行うことで成立させてきた:

1. `python3 -m http.server`でローカル配信
2. Node版Playwright（プリインストール済みChromiumを使用）でブラウザ操作を自動化したスクリプトを
   その場で書き、DOM状態・リンク遷移・クリック後の挙動を確認
3. 確認できたらユーザーに報告し、コミット許可を得る

このドキュメントは、(A) 現状の手動確認をいつでも同じ手順で再現できるようにチェックリスト化すること、
(B) 将来的に自動テストを導入する際の設計方針を示すこと、の2つを目的とする。

## 1. テスト環境の準備

### 1.1 ローカルサーバー起動

```bash
cd /path/to/NewsPortal-DEC/site
python3 -m http.server 8910
```

`http://localhost:8910/index.html` 等でアクセスする。

### 1.2 Playwright（Node版）の使い方

このプロジェクトの開発サンドボックス環境では、Playwrightはグローバルにインストール済みで、
Chromiumは `/opt/pw-browsers/chromium` にプリインストールされている
（`playwright install`は不要、むしろ実行してはいけない＝再ダウンロードが走り環境を壊す）。

```js
// check.js の例
const { chromium } = require('/opt/node22/lib/node_modules/playwright');
(async () => {
  const browser = await chromium.launch({ executablePath: '/opt/pw-browsers/chromium' });
  const page = await browser.newPage({ viewport: { width: 1280, height: 900 } });
  await page.goto('http://localhost:8910/index.html');
  await page.waitForTimeout(1200);
  // ここに検証コードを書く
  await browser.close();
})();
```

```bash
node check.js
```

**注意**: このサンドボックス環境ではGoogle Fonts（Material Symbols Outlined含む）に到達できないため、
アイコンがテキストのまま表示される（例: `zoom_in`という文字列がアイコンの代わりに出る）。
これは環境固有の制約であり、本番のGitHub Pages環境では発生しない。テストの合否判定に含めないこと。

### 1.3 収集スクリプト（`collect.py`）のローカル実行に関する注意

開発サンドボックス環境からは外部サイト（官公庁RSS等）に到達できないため、`collect.py`を
ローカルで実行してもほぼ全件が取得失敗になる（想定内の挙動で、エラーにはならず0件のまま完了する）。
**収集ロジックの実際の動作確認は、GitHub Actions上（`workflow_dispatch`での手動実行）で行う。**

診断が必要な場合は、`print(..., file=sys.stderr)`で診断ログを仕込んだ状態でコミット・pushし、
Actions実行後に`get_job_logs`相当の手段でログを確認する、というサイクルを使う
（`collect.py`内には既にこのパターンで書かれた診断ログが多数残っている）。

一時的な調査が必要な場合（URLの実在確認、リンク構造調査等）は、使い捨ての診断用ワークフロー
（例: `tmp-url-check.yml`）と診断スクリプトを作り、**調査完了後は必ず削除する**。

## 2. 手動確認チェックリスト（画面別）

変更の種類に応じて、影響するページのみ確認すればよい。全ページ共通の項目は「共通」を毎回、
機能追加時は関連する行を確認する。

### 2.1 共通（全ページ）

- [ ] コンソールエラーが出ていない（`page.on('pageerror', ...)`および`page.on('console', msg => msg.type()==='error')`で捕捉）
- [ ] `data-include`のパーシャル（masthead/footer等）が正しく読み込まれている
- [ ] `<title>`が正しいページタイトルになっている
- [ ] ナビゲーション（`search-tabs`のすべて/ニュース/ダッシュボード/用語集）に現在ページのハイライトが付く
- [ ] 375px幅（スマホ想定）で`document.body.scrollWidth === window.innerWidth`（横方向のoverflowがない）
- [ ] 表示設定パネル（文字サイズ/テーマ/サムネイル/カラー）を開閉でき、選択が`localStorage`に保存される
- [ ] リロード後も表示設定が保持される

### 2.2 `index.html` / `mobile.html`（トップページ）

- [ ] 新着ニュースのタブ切り替え（総合/国/自治体/…）で表示内容が変わる
- [ ] KPIストリップ4枚が表示され、各カードの参照元リンクが正しいURLを指している
- [ ] 技術キーワードショートカットをクリックすると`?tag=`付きで遷移し、該当タグの記事のみ表示される
- [ ] 検索ボックスにキーワードを入力してEnter/検索ボタンで`?q=`付き遷移し、該当記事のみ表示される
- [ ] カテゴリナビ（左サイドバー or mobileのカテゴリ帯）で`?cat=`遷移し、フィルタが効く
- [ ] フィルタ適用中は`filterChip`が表示され、「解除」ボタンで無フィルタ状態に戻る
- [ ] 「もっと読み込む」でニュース一覧が追加表示され、末尾まで達すると「これ以上の記事はありません」表示になる
- [ ] 記事カードのリンク先が正しい（`source_url`があればそれ、無ければ`article.html?id=`）
- [ ] 記事画像が正しく表示される、または画像なし記事はカテゴリ別フォールバック（写真/アイコン）が表示される

### 2.3 `news.html`

- [ ] index.htmlと同じニュース関連機能（タブ・検索・フィルタ・もっと読み込む）が同様に動作する
- [ ] KPIストリップ・右レールが表示されない（index.htmlとの差分どおり）こと

### 2.4 `dashboard.html`

- [ ] KPI4枚（CO2排出量/再エネ比率/カーボンプライス/ゼロカーボン宣言）が表示される
- [ ] 6種のグラフ（棒/折れ線×2/横棒×2/タイルグリッド×2）がすべて描画される
- [ ] 「静的データ」バッジが該当するカードにのみ表示される
- [ ] 各グラフの`src-line`（参照元・基準日）が表示される
- [ ] ゼロカーボンシティ宣言状況マップ・再エネ導入比率マップの47都道府県タイルが正しい位置に配置される
- [ ] 375px幅でタイルグリッド・SVGグラフがコンテナ内に収まる（overflowしない）
- [ ] 820px以下の幅で各グラフ/マップをタップすると拡大モーダルが開き、閉じるボタンまたは背景クリックで閉じる
- [ ] モーダル内でタイルグリッドの内容（名前・数値・バー等）が正しくレイアウトされている（改行・文字切れがない）

### 2.5 `glossary.html`

- [ ] 用語一覧がアコーディオンで開閉できる
- [ ] ページ本編にのみ「未登録: N件」の件数表示があり、右レール簡易版には出ない

### 2.6 `article.html`

- [ ] `?id=`が不正/未指定の場合に「記事が見つかりませんでした」表示になる
- [ ] 正しい`id`で記事本文・タイトル・パンくずが表示される
- [ ] ブックマークボタンでON/OFFが切り替わり、`localStorage`（キー`dn-bookmarks`）に反映される
- [ ] 印刷ボタンで`window.print()`が呼ばれる（ダイアログの発生確認のみでよい）
- [ ] 共有ボタンでWeb Share API（対応環境）またはクリップボードコピー（非対応環境）が動作する

### 2.7 右レール／脱炭素行政ダイジェスト（`partials/rail.html`を含むページ）

- [ ] 「本日の新着（官公庁）」の件数リンクが`news.html?cat=national&date=today`を指す
- [ ] 政策スケジュールが直近4件、日付順に表示される（過去日は出ない）
- [ ] 公募中の補助金一覧が表示される（0件の場合は「収集中…」表示になる）
- [ ] イベント・セミナー一覧が開催日順に表示される（過去開催日のものは出ない）
- [ ] 話題のキーワードランキングが表示され、クリックで`?q=`検索に遷移する

## 3. 収集スクリプト（`collect.py`）の検証観点

GitHub Actions上での実行結果（Actionsログ、および更新後のJSON差分）で確認する。

### 3.1 正常系

- [ ] `articles.json`が更新され、新規記事数・合計記事数が末尾ログ（`収集完了: 新規 X 件 / 合計 Y 件`）に出力される
- [ ] `feed.json`/`categories.json`/`topics.json`/`ranks.json`/`events.json`/`meta.json`が整合して更新される
- [ ] `categories.json`の各`count`が、`articles.json`内の実際のカテゴリ別件数と一致する
- [ ] 週1回間引き対象（ゼロカーボン宣言数、再エネ導入比率）が、間引き期間中は`[skip]`ログのみで
      既存データを変更しないこと

### 3.2 異常系・フォールバック

- [ ] 個別の収集元フィードが取得失敗しても、他の収集元の結果には影響しない（`[skip] {name}: 取得失敗`ログ）
- [ ] PDF/Excel解析に失敗した場合、該当データのみ前回値を保持し、他のデータ更新は継続する
- [ ] JEPX CSV取得・解析に失敗した場合、`rail-data.json`の卸電力価格が前回値のまま変わらない

### 3.3 データ品質（過去に不具合が見つかった観点。回帰確認用）

- [ ] キーワードマッチングが英単語の一部に誤爆していないか（例: 過去に`EV`が`SEVENTEEN`の一部に
      マッチした事例がある。新しいキーワードを`KEYWORDS`に追加する際は、英数字のみのキーワードに
      `_keyword_pattern`の単語境界チェックが適用されることを確認する）
- [ ] 同一記事が複数IDで重複登録されていないか（`dedupe_by_title`の正規化キーで重複確認）
- [ ] 都道府県別データ（ゼロカーボン宣言・再エネ導入比率）の合計値が
      `ZERO_CARBON_PLAUSIBLE_RANGE`等の妥当範囲チェックを通っているか（範囲外の値は採用されず`[skip]`になる）
- [ ] 再エネ比率の算出式（水力+風力+太陽光+地熱）にバイオマス・廃棄物を再度混入させていないか
      （過去に誤加算バグがあった箇所。`fetch_renewable_ratio_by_prefecture`のコメントに経緯が残っている）

## 4. 回帰チェック項目（過去に見つかった不具合の再発防止）

| # | 不具合 | 原因 | 確認方法 |
|---|---|---|---|
| 1 | モバイル幅でタイルグリッド/SVGグラフがコンテナからはみ出す | `grid-template-columns:repeat(N,1fr)`がテキスト最小幅で押し広げられる | 375px幅で`document.body.scrollWidth === window.innerWidth`を確認 |
| 2 | タップ拡大モーダル内でスタイルが効かない（バー消失・文字結合） | `#id .class`のCSSスコープがモーダル（`document.body`直下）に届かない | モーダルを開いた状態で対象要素の`getComputedStyle`が期待通りか確認 |
| 3 | 再エネ比率にバイオマスが二重計上される | Excel列の意味を検算せず「バイオマス＝再エネ」と誤解 | 都道府県ごとに手計算し、`K列(新エネ計)`と一致するか確認 |
| 4 | 政策スケジュールのURLが誤り（推測で入力） | 実在確認をせずにデータ投入した | 新規URLをデータに追加する際は必ず実在確認（curl/WebFetch等）を先に行う |
| 5 | 無関係な芸能ニュース（BTS関連PR）が脱炭素記事として混入 | `EV`キーワードが`SEVENTEEN`等の英単語に部分一致 | 新しい短い英字キーワードを追加する際、単語境界チェックが効いているか確認 |
| 6 | 用語集の凡例表記が「0%～50%～100%」など冗長だった | UI文言の見直し漏れ | 凡例・ラベル文言は都度目視確認する |

## 5. 自動テスト導入の提案（将来対応）

現状は完全に手動確認に依存しているため、以下の段階的な自動化を提案する。優先度が高い順。

### 5.1 優先度高: 収集スクリプトの単体テスト

`collector/collect.py`の純粋関数（外部通信を伴わないもの）はテストしやすい。`pytest`導入を推奨。

対象候補:
- `_keyword_pattern` / `KEYWORD_RE`（誤検知の回帰テスト。`SEVENTEEN`にマッチしないこと等をケース化）
- `parse_date` / `format_time`
- `normalize_title_for_dedup` / `dedupe_by_title`
- `classify_category`（CATEGORY_RULESの優先順位確認）
- `extract_event_date`
- `count_zero_carbon_by_prefecture`（サンプルPDFテキストを固定文字列で用意）
- `find_latest_renewable_sheet`
- `fetch_renewable_ratio_by_prefecture`の集計ロジック部分（openpyxlのワークブックをモック、
  またはサンプル.xlsxをテストフィクスチャとして`collector/tests/fixtures/`等に置く）

外部通信を伴う関数（`fetch`、`fetch_zero_carbon_total`等）は、`urllib.request.urlopen`を
モックしてレスポンスを差し替える形でテスト可能。

### 5.2 優先度中: フロントエンドのE2Eテスト（Playwright Test化）

現状「その場でPlaywrightスクリプトを書いて捨てる」運用をしているが、`@playwright/test`を
`package.json`に導入し、2章のチェックリストをそのままテストケース化すれば、CI
（例えばPull Request時にGitHub Actionsで実行）で回帰確認が自動化できる。

構成イメージ:
```
tests/
  e2e/
    top-page.spec.js       # 2.2の項目
    dashboard.spec.js      # 2.4の項目
    article.spec.js        # 2.6の項目
    mobile-overflow.spec.js # 375px幅でのoverflow確認（回帰チェック#1）
playwright.config.js
```

注意点: サイトはデータ駆動（`site/data/*.json`をfetch）なので、テストは実データの内容に依存しすぎない
アサーションにする（例: 「KPIカードが4枚表示される」「グラフのsvgが存在する」等の構造確認を主にし、
数値そのものの厳密一致は避ける）。

### 5.3 優先度低: JSON Schemaによるデータ整合性チェック

`site/data/*.json`の構造をJSON Schemaとして定義し、収集スクリプト実行後・コミット前に検証する
GitHub Actionsステップを追加する。フロント側が期待するフィールドが欠落した状態でコミットされる事故を防げる。

### 5.4 導入時の注意

- CLAUDE.mdの「指示された範囲を超えた追加の修正はしない」方針がある以上、テスト導入自体も
  ユーザーの明示的な依頼を待って着手すること（本ドキュメントはあくまで「提案」であり、
  無断でテスト基盤を追加してよいという意味ではない）。
- 依存パッケージを追加する場合（`pytest`、`@playwright/test`等）は、GitHub Actions側の
  セットアップ工数・実行時間増加とのトレードオフを事前にユーザーと合意する。

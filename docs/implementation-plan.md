## 1. アーキテクチャ概要

```
[GitHub Actions: collect-decarbon-news.yml] --3時間毎--> collector/collect.py
        |                                                       |
        | 官公庁RSS/Atom, Googleニュース検索RSS,                | 書き込み
        | 環境省HTML/PDF, 資源エネルギー庁Excel, JEPX CSV      v
        └----------------------------------------------> site/data/*.json
                                                                 |
                                                     git commit & push (自動)
                                                                 |
                                                                 v
                                        [GitHub Actions: deploy-pages.yml] --push契機-->
                                                                 |
                                                                 v
                                                    GitHub Pages（静的ホスティング）
                                                                 |
                                                                 v
                                        ブラウザ: site/*.html が site/data/*.json を fetch して描画
```

- **ビルドステップなし**。`site/`配下は`python3 -m http.server`等で直接配信可能な素のHTML/CSS/JS。
- **バックエンドAPIなし**。データ取得はすべてブラウザ側の`fetch()`によるJSON読み込み。
- **収集とデプロイは疎結合の2ワークフロー**（`collect-decarbon-news.yml`が変更検知後に
  `deploy-pages.yml`をworkflow_dispatchで能動的にキックする）。

## 2. 実装履歴（フェーズ別サマリ）

以下は時系列で実際に行われてきた実装の要約。詳細な一つ一つのやり取りは会話ログにしかないため、
「何を」「なぜ」やったかの結論だけを残す。

### フェーズ1: 土台構築
- Claude Designでエクスポートされた静的デザイン一式（`site/`）と、収集スクリプト（`collector/`）を
  リポジトリ直下に配置。
- GitHub Actionsワークフロー2本（収集・デプロイ）を新規作成し、収集→コミット→デプロイの自動パイプラインを確立。
- `topics.json`/`ranks.json`をデザイン時の静的サンプルから、収集データを元にした自動生成に切り替え。

### フェーズ2: 実データ連携の拡充
- ゼロカーボンシティ宣言自治体数（総数）、JEPXスポット卸電力価格を実データ取得に対応。
  取得失敗の原因調査には「診断ログを仕込んだ状態で本番ワークフローを実行し、Actionsログで実際の
  HTML/CSV構造を確認する」というアプローチを繰り返し使っている（サンドボックス環境が外部に
  到達できないため）。
- 記事サムネイル画像をOGP（`og:image`/`twitter:image`）から取得する仕組みを追加。取得失敗時は
  カテゴリ別のフォールバック画像/アイコンを表示。

### フェーズ3: ブランディング・UI再設計
- サイト名を「脱炭素ナビ」から「脱炭素ニュースポータル」へ全ページ変更。
- ミニゲージ削除、表示設定パネルの簡略化、カテゴリ別ストック写真の反映。
- 実在しない/機能していない要素（「あなたの地域」ブロック、モバイル版の偽再エネ比率ティッカー、
  「このサイトについて」等の未実装リンク）を削除し、「見た目だけの静的ダミー」を排除する方針を徹底。

### フェーズ4: 検索・フィルタ・パーソナライズ機能の実装
- 検索ボックス実機能化、トピックタブのカテゴリフィルタ接続、話題のキーワード・記事タグからの検索連携。
- ブックマーク機能（localStorage）、印刷・共有ボタン、「すべて見る」「トピックス一覧」展開表示。
- 用語集のアコーディオン化。

### フェーズ5: カテゴリ体系・タグ体系の再設計
- カテゴリを新体系（総合/国/自治体/企業/技術/暮らし/国際/その他、のち「先行地域」を追加）に変更。
- 技術要素ショートカット（`shortcuts.json`）をタグベースのフィルタに刷新。

### フェーズ6: データダッシュボードの新設
- KPI4枚に参照元リンク・基準日を追加。`dashboard.json`に`charts`メタデータブロックを新設し、
  各グラフの参照元をUIに表示する仕組みを整備。
- 環境省「ゼロカーボンシティ取組一覧」PDFを解析し、都道府県別の宣言件数を集計する処理を実装
  （診断ログ版→実PDF構造確認→正式パーサーの順で段階的に実装。市区町村数の分母は固定テーブルで保持）。
- 47都道府県タイルグリッド地図（カートグラムのrow/col座標配置）を設計し、ゼロカーボンシティ宣言状況の
  可視化に採用。

### フェーズ7: 脱炭素行政ダイジェスト（地方公共団体職員向け特化ブロック）
- ユーザーからの提案依頼を受け、「地方公共団体職員にとって実務的に有用な情報」という切り口で
  右レールの「きょうの指標」を刷新。本日の新着（官公庁）件数・政策スケジュール・公募中の補助金一覧、
  の3点構成に再設計。
- `collect.py`に環境省・NEDO・経産省の公募情報スクレイパーを追加。
- 政策スケジュールのURLは、当初推測で入力してしまいユーザー指摘を受けた反省から、
  一時的な調査用ワークフローで実在確認したうえで正しいURLに差し替える運用に切り替えた
  （詳細は本ファイル4章「教訓」を参照）。

### フェーズ8: 用語集の自動候補収集
- 話題のキーワードのうち用語集未登録のものを`glossary_pending.json`に集める仕組みを追加。
  定義文の自動生成はできないため、あくまで人手確認・登録の候補リストとして扱う設計にした
  （サイト上は件数のみ表示し、内容そのものは公開しない）。

### フェーズ9: 都道府県別再エネ導入比率マップ
- 資源エネルギー庁「都道府県別発電実績」Excelファイルをデータソースとして採用。
  実際のExcel構造をユーザーが添付ファイルで提供し、それを解析することで列構成（水力/火力/原子力/
  風力/太陽光/地熱/バイオマス/廃棄物/蓄電池/新エネ計/その他/合計）を確定させた。
- **バイオマス誤加算のバグ修正**: 当初「再エネ比率＝水力+風力+太陽光+地熱+バイオマス」としていたが、
  実データ検証の結果、バイオマスは火力発電の内訳としての再掲であり、新エネ計（風力+太陽光+地熱+
  蓄電池のみ）と一致しないことが判明。バイオマスを再エネ比率の計算から除外する修正を行った
  （このバグ修正はユーザーからの厳重注意を受けた後の対応であり、経緯は4章参照）。
- 表示は当初ニュース一覧ページ末尾だったが、後に「データダッシュボードのみに一本化」という
  ユーザー要望を受けてトップページ・ニュースページから削除し、`dashboard.html`のみに残した。
- 発電量の桁差（都道府県間で300倍以上）を可視化するため、対数スケールのバーをタイル右側に追加。
- コンパクト表示（タイルグリッド）とタップ拡大モーダル表示とでCSSスコープが異なる問題
  （`#renewable-map .rn-tile`のようなIDスコープ付きセレクタが、モーダルが`document.body`直下に
  クローンされることで効かなくなる）を発見し、クラスセレクタへ変更して解消。

### フェーズ10: モバイル対応の底上げ
- 文字サイズ設定が実際にCSS全体へ反映されるよう`--fs-d`/`--fs-dl`カスタムプロパティの適用漏れを修正。
- CSS Gridの`repeat(N,1fr)`がテキストコンテンツの最小幅によってコンテナをoverflowさせるバグを発見し、
  `repeat(N,minmax(0,1fr))`に統一して解消（タイルグリッド系コンポーネント全般に影響していた）。
- モバイル幅（820px以下）でグラフ・マップをタップ拡大表示する共通機構（`DN.enableTapToZoom`）を新設。

### フェーズ11: データ品質の是正
- キーワードマッチングの誤検知（`EV`が`SEVENTEEN`等の無関係な英単語の一部にマッチしていた）を発見し、
  英数字のみのキーワードには単語境界チェックを追加。既に混入していた無関係記事をデータから手動削除。

## 3. 主要な設計判断とその理由

| 判断 | 理由 |
|---|---|
| ビルドステップ無しの素のHTML/CSS/JS | GitHub Pagesにそのままデプロイでき、依存関係の管理コストがゼロ。デザイン(Claude Design)由来の構成をそのまま活かせる |
| データを`site/data/*.json`に完全分離 | 表示とデータを分離することで、収集スクリプトの改修がフロントに影響しない。テーマを差し替える際もJSON差し替えのみで済む |
| 収集元を`sources.json`に外部化 | コードを変更せずに収集対象の追加・削除ができる。`feed`（固定URL）と`search`（Googleニュース検索RSS）の2パターンを混在可能にし、専用フィードを持たない対象も拾えるようにした |
| 記事の同一性をタイトル正規化で判定（URLハッシュではない） | 検索RSS経由だと同じ記事でもクエリ毎に別URL（別トラッキングリンク）が発行されるため、URLベースの重複排除では機能しない |
| 「自動生成データ」と「手動管理データ」の明確な分離 | 収集スクリプトが誤って手動管理データを上書きする事故を防ぐ。`collect-decarbon-news.yml`の`git add`対象リストが実質的な仕様書になっている |
| 外部データ取得の「失敗時は前回値保持」方針 | cron実行が前提のため、一時的な外部障害でサイト全体の更新が止まる／エラーになるのを防ぐ |
| ゼロカーボン宣言数・再エネ比率を週1回に間引き収集 | 変動が少ない統計データを毎回（3時間毎）取得する必要がなく、対象サイトへの負荷も抑えられる |
| キーワード判定に単語境界チェックを追加（英数字キーワードのみ） | 短い英字略語（EV等）が無関係な英単語の一部にマッチする誤検知を防ぐため。日本語キーワードは英数字と隣接しないため対象外でよい |
| CSS Gridは`minmax(0,1fr)`を必須にする | `1fr`単体だとテキストの最小コンテンツ幅がトラックの下限になり、コンテナをoverflowさせる既知の落とし穴 |
| タップ拡大モーダルはクラスセレクタでスタイリング | モーダルは`document.body`直下にクローンされるため、`#id .class`のようなIDスコープ付きCSSが効かない |

## 4. 教訓・注意点（再発防止のための記録）

1. **URLは推測せず必ず実在確認する。** 政策スケジュールのURLを推測で入力した結果、後から誤りが
   発覚した経緯がある。以降、未検証の外部URLをデータに組み込む際は、一時的な調査用GitHub Actions
   ワークフロー（`tmp-url-check.yml`のような使い捨てワークフロー＋診断スクリプト）を作り、実際に
   到達確認・構造確認をしてから正式に採用し、調査用ワークフローは使用後に削除する運用とする。
2. **ユーザーの明示的な承認を得るまで、コミット・pushはおろか実装の続行もしない。** 過去に
   「OKと言っていないのに勝手に進めた」ことでユーザーから厳重注意を受けた経緯がある。
   `AskUserQuestion`でのUIオプション提示や、Stop hookの自動メッセージだけを承認の根拠にしない。
   曖昧な場合は明示的に問い直す。
3. **データの意味を機械的に信じず、実データで検算する。** 再エネ比率のバイオマス誤加算は、
   Excelの列名だけを見て「バイオマス＝再エネ」と機械的に判断したために起きたバグ。実際に
   都道府県ごとの内訳を手計算して既存の集計列と突き合わせることで発見できた。
4. **CSSのスコープ設計は、要素がDOM上で移動・複製されるケース（モーダル等）を考慮する。**
   IDスコープの詳細度に頼ったCSSは、要素が別の親にクローンされた瞬間に壊れる。

## 6. 開発フローの型（`skills.md`より抜粋・要約）

1. **診断**: grepで関連箇所（HTML要素のid、対応するJS関数、対応するJSON）を特定する。
2. **実装**: 既存のヘルパー（`DN.fetchJSON`/`DN.esc`等）・既存の描画パターンに揃えて書く。新しい仕組みを増やさない。
3. **ローカル動作確認**: `python3 -m http.server`でsite/を配信し、Playwright（Node版、
   プリインストール済みChromiumを`executablePath`指定で使用）でDOM・リンク遷移・クリック後の挙動まで確認する。
4. **提示と確認**: `git diff`と変更内容の要約をユーザーに提示し、明示的な許可を得てからコミットする。
5. **コミット**: 日本語、「何を」だけでなく「なぜ」を書く。1依頼＝1コミットを基本とする。
6. **push前の差分確認**: pushする前に対象ブランチをfetchし、収集ボットの自動コミットと衝突していないか
   確認する。競合していたら`git pull --no-rebase`（マージコミット）で取り込んでからpushする
   （force push/rebaseは使わない）。

このプロジェクトでは収集ボット（GitHub Actions）が同じ作業ブランチに自動コミットしてくる構成のため、
push前のfetch確認とマージは「例外対応」ではなく「毎回のルーティン」として扱う。
